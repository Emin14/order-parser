# Правила сборки заказов для экспорта в Word

Этот документ описывает, как сырые заказы из мессенджеров (VK, Telegram, WhatsApp) превращаются в готовый документ для Word.

## 0. Единый сбор на рабочую дату
При запуске парсер рассчитывает единый контекст текущего сбора в `src/utils/collection.ts`: режим, дату поставки, границы смены и включённые календарные периоды. VK, Telegram и WhatsApp используют общую проверку `isMessageInCollection`; различается только разбор даты из интерфейса конкретного мессенджера. Воскресенье не является отдельным рабочим днём: накопленные воскресные сообщения входят в понедельничный сбор.

В дневном режиме (06:00–17:59) сегодняшние сообщения принимаются без автоматического отсечения в 15:00. Правила прошлых дней и переключение режима в 18:00 сохраняются. Ограничить время окончания Word-экспорта можно явно через `TO_TIME`. Граница 15:00 в правилах отображения времени и очистки срока поставки не меняется.

Пересланные сообщения VK сохраняются как один заказ. Для отбора используется время появления пересылки в текущем чате, а в экспорт добавляется подпись с датой и временем исходного сообщения: `пересланное сообщение от 22.10.2026 00:12:`. Исходный текст сохраняется целиком.

Если у пересланного сообщения есть внешний текст, одна непустая строка без вводных слов считается заголовком и ставится перед пересылкой. Цифры в такой строке разрешены, чтобы корректно обрабатывать адреса (`Татарская 2`, `Соборная 15а`). Строка с отдельным `+` считается добавкой и ставится после пересылки; телефонный префикс `+7` этому правилу не мешает. Остальной внешний текст также выводится после пересылки.

### Дополнительный диапазон `FROM_TIME` / `TO_TIME`

Диапазон ограничивает Word-экспорт после обычного сбора, перед объединением сообщений. Исходный `orders.json` сохраняет все собранные сообщения. Параметры `--from HH:MM` и `--to HH:MM` перекрывают соответствующие константы в `src/index.ts`; формат проверяется до запуска браузера.

Начало диапазона — последнее наступившее указанное время по локальным часам компьютера:

- `00:00` — сегодня с полуночи;
- `10:00` при запуске в 16:00 — сегодня с 10:00;
- `23:00` при запуске в 10:00 — вчера с 23:00.

`TO_TIME` по умолчанию пустое: окончание — момент экспорта. Если указаны обе границы, окончание относится к дате начала, а время меньше начала означает следующий день. Например, при запуске в 10:00 `23:00–02:00` означает вчера с 23:00 до сегодняшних 02:00. Одинаковые границы означают один указанный момент, а не сутки. Будущая часть любого диапазона не включается.

Если задано только `TO_TIME = '15:00'`, конец — сегодня в 15:00; принятые общим сбором прошлые дни сохраняются. Чтобы ограничить только сегодняшний день, нужно также задать `FROM_TIME = '00:00'`. Для сбора по 15:00 включительно: `FROM_TIME = '00:00'`, `TO_TIME = '15:00'`. Обе пустые строки отключают дополнительный фильтр.

Дата и время сообщения сравниваются с границами включительно. Для пересылки используется дата её появления в текущем чате. Единая реализация для VK, Telegram и WhatsApp находится в `src/utils/top_up.ts`. Фильтр диапазона не расширяет правила сбора прошлых дней.

Для старых данных без распознанной даты сохраняется прежнее предположение по часам: время позже текущего относится ко вчерашнему дню. Если время неизвестно, сообщение сохраняется только при подходящей известной дате; при отсутствии обоих значений сохраняется, чтобы не потерять текст. Точный отбор таких неполных данных невозможен. Диагностика `top-up-filter` в `export_detail.log` показывает границы, количество принятых сообщений и сообщений без даты. Некорректный формат времени вызывает понятную ошибку.

## 1. Очистка названия кафе (без служебных слов)
Из названий чатов автоматически удаляются слова «заказы», «овощи», «фрукты», «овощи/фрукты», «овощи и фрукты», а также эмодзи.
- *«Бостон заказы овощи»* → **«Бостон»**
- *«Заказы овощи/фрукты Sherri»* → **«Sherri»**
- *«Заказы Кавалли»* → **«Кавалли»**

## 2. Разделение одиночных и общих чатов
- **Одиночные чаты (`shared_chat: false`)**: Заголовком заказа становится очищенное название чата.
- **Общие сборные чаты (`shared_chat: true`)**: Название самого чата игнорируется. Заголовок берётся из первой строки сообщения, которую пишет сам клиент (например, **«В грузинку»**, **«ООО Хорошие Руки Рыба, Семинарская 1»**).
- **Fallback (если клиент забыл указать точку)**: Если в сборном чате первое слово — это сразу товар (помидоры, картошка), то в качестве названия используется очищенное название чата, а не имя автора.

## 3. Заголовок всегда в одну строку с двоеточием в конце
Независимо от того, как клиент переносил строки (например, название юрлица, а потом адрес), заголовок склеивается в одну строку и заканчивается двоеточием: `Зерно плаза ИП Волков:`

## 3.1. Исходное или каноническое имя филиала (`use_branch_name`)
По умолчанию парсер сохраняет строку филиала так, как её написал пользователь. Если в настройках чата указать `"use_branch_name": true`, найденный филиал выводится под каноническим именем из `branches`.

Например, при таких настройках:

```json
"branches": [
  { "name": "Мангал Почтовая", "aliases": ["почтовая", "солотча"] }
],
"use_branch_name": true
```

сообщение с заголовком `Почтовая:` будет выведено как `Мангал Почтовая:`. Алиасы продолжают использоваться для распознавания и объединения заказов.

## 3.2. Очистка приветствий
Очистка выполняется в два шага. Список фраз, которые удаляются целиком, проверяется во всех строках сообщения. Регистр, пробелы и знаки препинания не учитываются: `Адам`, `Асиман`, `заявка`, `овощи`, `ба`, `спасибо`. Поэтому `Заявка:`, `А-СИМАН` и `ОВОЩИ!` удаляются, а `Заявка на завтра` сохраняется. Список приветственных и вводных фраз, включая `примите пожалуйста заказ` и `примите заказ`, проверяется только в первых трёх непустых строках: совпавшая фраза удаляется внутри строки вместе с прилегающими пробелами и знаками препинания. После этого строка повторно проверяется по списку целых строк, чтобы удалить оставшуюся фразу: например, `Добрый день! Адам` превращается в пустую строку. Остальной текст строки сохраняется.

Вводные варианты `примите пожалуйста заявку`, `примите заявку пожалуйста`, `примите заявку` очищаются тем же списком. Сохранение `Заявка на завтра` на этапе целых служебных строк не отменяет последующую проверку срока поставки из раздела 3.3.

В чатах с `branches` филиал ищется в первых трёх непустых строках полностью. Товары для этого не анализируются. Если филиал найден во второй или третьей строке, все предыдущие строки и строка с филиалом включаются в заголовок. Это позволяет обработать переносы вроде `в` на первой строке и `маленькую соду на завтра` на второй.

Если для чата включён `use_branch_name`, каноническое имя филиала используется в заголовке и при объединении, но очищенный текст вокруг найденного названия филиала не удаляется: он переносится в начало текста заказа. Приветствия и служебные фразы, удалённые на этапе очистки, обратно не возвращаются.

## 3.3. Удаление вводного срока поставки

Вместо отдельного правила «на завтра после 15:00» используется `stripDeliveryPhrase` из `src/utils/delivery_rules.ts`. В `DELIVERY_RULES` единообразно заданы граница 15:00, воскресенье как выходной, лимит трёх непустых строк, названия/сокращения дней недели и всех 12 месяцев. Справочник месяцев общий с распознаванием дат мессенджеров; формы вроде `мая` также распознаются.

Очистка проверяет начало каждой из первых трёх непустых строк после удаления приветствий: `на завтра`, `на понедельник`, `на пн`, `на 2.11`, `на 02.11.2026`, `на 2 ноября`, `на 2 ноября 2026`, `на 2 ноя.`, а также варианты с `заказ`, `заказы`, `заявка`, `закупка`. Обычные и неразрывные пробелы допускаются. Например, `Заявка на 2 ноября` удаляется, если текущая поставка — 2 ноября. Предыдущая строка с `ИП Каюмова` сохраняется. `Заказ на понедельник ИП Лутикова Екатерина` превращается в `ИП Лутикова Екатерина`. Четвёртая и последующие непустые строки не проверяются; срок в середине строки с комментарием не вырезается.

Сообщение должно входить в окно срока поставки: с предыдущего рабочего дня 15:00 (включительно) до дня поставки 15:00 (не включительно). Для понедельника это суббота 15:00 — понедельник 15:00, включая всё воскресенье. Это границы времени сообщений, а не переключения режима запуска. Дата текущей поставки для очистки меняется в 18:00, как режим сбора; между 15:00 и 18:00 продолжает обрабатываться дневная поставка. Поэтому при запуске в понедельник в 16:26 вводные сроки воскресных заказов на понедельник всё ещё удаляются. Часы 15:00 и 18:00 заданы в общем `DELIVERY_RULES` как `boundaryHour` и `collectionChangeHour`. Используется дата и время исходного сообщения, а не только его час. Поэтому ранние субботние сообщения не очищаются как понедельничные. Если дата сообщения отсутствует, используется день запуска; неизвестная дата или отсутствующее/некорректное время не дают оснований для очистки.

Указанный день недели или число должны совпасть с поставкой; год, если указан, тоже проверяется. Для «завтра» берётся следующий день после исходного сообщения с переносом воскресенья на понедельник. Другой срок и указания внутри комментариев сохраняются. Во вторник вечером `на среду` удаляется, `на пятницу` остаётся.

Это окно используется для очистки текста. Оно не изменяет отбор сообщений в `isMessageInCollection` или переключение режима запуска в 18:00. Старая зависимость очистки от `deliveryDate`, переключавшегося в 12:00, удалена.

## 4. Время заказа с 06:00 до 15:00
Формирование отметок выполняется общей функцией `formatCollectionBlocks` из `src/utils/collection.ts`; экспортёр не содержит отдельной логики смены.
Для сообщений, которые поступили с 06:00 до 14:59, время выводится **внутри самого заказа** только перед первым утренним сообщением. Ночные сообщения с 00:00 до 05:59 временем в заказе не помечаются.
Когда выводится дата сообщения, перед ней добавляется день недели: `(сб 31.10 11:21)`. Используются сокращения `пн`, `вт`, `ср`, `чт`, `пт`, `сб`, `вс`. Каждое сообщение старой части получает собственную дату и время, даже если другие сообщения в этом заказе или чате имеют ту же дату.

При разделении сообщения по «Отдельной накладной», «Отдельным чеком» или «Отдельно» самостоятельный блок сохраняет дату и время исходного сообщения и получает отметку на общих основаниях. Отдельного исключения для повторения даты у накладных нет. Правила отметок только времени у актуальных сообщений не меняются.

Для отображения воскресного и понедельничного сбора до понедельника 18:00 суббота с 15:00 и всё воскресенье считаются одной актуальной частью. Субботние сообщения до 15:00 относятся к старой части и получают дату и время. Если в объединённом заказе перед актуальной частью есть старые сообщения, требующие отметки даты или времени, первое сообщение актуальной части получает отметку: время, если оно пришло сегодня, либо день недели, дату и время, если в другой день. Отметка перехода выводится даже когда эта дата уже была напечатана ранее в чате. Последующий переход с субботы на воскресенье сам по себе новых отметок не создаёт. Если старой части нет, субботний вечер и воскресенье выводятся без отметок.

Например, при запуске в понедельник: `(сб 31.10 11:21)` — старая часть, `(сб 31.10 20:45)` — начало актуальной части, затем воскресное продолжение в 15:51 идёт без новой отметки. После понедельника 18:00 применяются обычные правила. Это только отображение: режимы запуска 06:00/18:00, отбор сообщений и объединение заказов не меняются.
Если заказы сливаются (`merge_same_spot`), последующие утренние сообщения остаются без повторной отметки времени.
**Важное дополнение:** Если в склеенном заказе есть хотя бы одно утреннее сообщение (с 06:00 до 14:59), то самое **первое** сообщение, поступившее после 15:00, тоже получит отметку времени, чтобы отделить его от утренних. Остальные вечерние сообщения останутся без времени.
Например:
```
Старый город:
(10:44)
Кинзу можно добавить - 0,5 кг

(18:22)
Укроп 200 г
Петрушка 500 г

Чили свежий 100 г
Кабачок 1 кг
```
Для обычного рабочего дня, если все сообщения актуального периода пришли после 15:00 и перед ними нет старой части с отметками, время не отображается ни у одного из них. Для выходных действует единая граница субботы 15:00, описанная выше.

## 5. Добавки и дозаказы без явной точки (по автору)
Если приходит сообщение, которое похоже на добавку (начинается со слова "добавка" или состоит только из товаров без названия точки), и в чате нет склейки по умолчанию, то этот дозаказ автоматически "прилипает" к последнему заказу **того же самого автора (отправителя)**.

## 6. Объединение сообщений одного отправителя
По умолчанию соседние сообщения одного отправителя в одном чате объединяются, если второе сообщение не содержит новый филиал и не является ответом на другое сообщение.

## 7. Администраторы мессенджеров
Глобальные массивы `<platform>.admin_names` в `cafes_config.json` содержат имена администраторов соответствующей платформы. Сообщения отправителей из этих массивов выводятся отдельными блоками под их именами. Чаты из `<platform>.admin_excluded_chats` используют старую обработку без имён администраторов. Нового администратора можно добавить отдельной строкой:

```json
"admin_names": [
  "Адам Агаев",
  "Имя нового администратора"
],
"admin_excluded_chats": [
  "Семья"
]
```

## 8. Маркеры составного заголовка
Для общих чатов можно использовать `header_markers` вместо `branches`. Маркеры представляют собой независимые организации, адреса, торговые центры или названия заведений. В первых четырёх строках сообщения ищется любой маркер; все строки до последнего найденного маркера становятся одним заголовком. Организации и адреса не связываются между собой.

Проверка первой строки по списку служебных слов и определение первой строки как товара больше не используются для распознавания заголовка. Например:

```json
"header_markers": [
  {
    "name": "Семинарская",
    "aliases": [
      "семинарская",
      "семинарскую",
      "на семинарскую",
      "семинарской"
    ]
  }
]
```

Флаг `merge_by_sender: true` включает расширенный режим: сообщения того же отправителя могут объединяться даже через промежуточные сообщения. Явно указанный новый филиал, ответ на сообщение и отдельная накладная всегда начинают отдельный блок.

Флаг применяется только в конкретном чате, где он указан в `cafes_config.json`.

## 6. Объединение заказов одной точки за смену (`merge_same_spot: true`)
Если флаг включен, все заказы для одной и той же точки сливаются в один список.
- *Исключение:* Если в тексте есть слово `Отдельно`, этот блок не сливается.

## 7. Разделение заказа по ключевому слову «Отдельно»
Если клиент пишет внутри заказа `Отдельно` и дальше список товаров, этот заказ физически разрезается на два:
1. `<Точка>:` (основные позиции)
2. `<Точка> Отдельно:` (позиции из блока «Отдельно»).

## 8. Разделение баров и кухонь
Если в тексте написано `Заказ бар:` и `Заказ кухня:`, алгоритм делит это на два независимых заказа под разными заголовками (например `<Точка> бар:` и `<Точка> кухня:`).

В чатах с `shared_chat: true` очищенный общий текст перед первым маркером соединяется с каждым маркером в одну строку заголовка: `Заказ на понедельник ИП Лутикова Екатерина Заказ бар:` и `Заказ на понедельник ИП Лутикова Екатерина Заказ кухня:`. Переносы внутри общего контекста заменяются пробелами, завершающее двоеточие контекста убирается. Товары остаются ниже заголовка. Пустой контекст или одно приветствие не добавляются; для обычных чатов поведение не меняется.

## 9. Добавление бренда к филиалу (`prefix_brand: true`)
Принудительно подставляет очищенное имя бренда к филиалу.
Например, в «Пиццерия Куба Заказы» из слова `Юбилейная` получается `Куба Юбилейная:`.

## 10. Форумы Telegram (`is_forum: true`)

При склеивании снимков истории Telegram сообщение сопоставляется по `data-message-id` самого элемента, либо по его ID вида `message-113972`. Если ID отсутствует, сравниваются отправитель, время и полный текст. Снимки сопоставляются как упорядоченные последовательности через наибольшую общую подпоследовательность (LCS): каждое совпадение используется только один раз. Поэтому одинаковые короткие сообщения не схлопываются в один якорь и не меняют порядок соседних заказов. Разделители дат сопоставляются по тексту в той же последовательности. ID записывается в снимки `telegram_spy.log`, а для первых трёх сообщений без ID — атрибуты `id` и `data-*` в записи `IDENTITY`. Это сопоставление при прокрутке не меняет правила объединения заказов по отправителю.
Для групп с подчатами заголовок собирается из `<Очищенный бренд> <Название топика>:`.
Например: `Хинкдом Премьер:`.

## 11. WhatsApp: объединение подряд идущих сообщений (`merge_consecutive_by_author: true`)
Если один и тот же человек отправляет несколько сообщений подряд (без ответов других людей между ними), они склеиваются в один длинный текст до применения остальных правил.

## 12. Разделение суб-заказов в одном сообщении (`split_sub_orders: true`)
Если в одном большом тексте клиент прислал заказы на несколько адресов через пустую строку (двойной перенос `\n\n`), текст режется на независимые заказы со своими заголовками.
